# 投資口座監査と復旧計画（2026-10-05）

## 調査体制

- 口座データ担当: SQLiteの整合性、口座別決済件数と損益を監査
- 取引ロジック担当: 銘柄別自動売買、損失停止、二重評価を監査・修正
- UI担当: 口座画面とAPIの項目対応を監査
- 統合担当: 状態保存、稼働中口座の移行、再起動後の検証

## 監査結果

SQLiteの `trades` には683件の決済履歴があり、重複ID、決済時刻の逆転、`gross_pnl - fee = net_pnl` の不一致は確認されなかった。これは決済行の内部整合性であり、売買判断の正しさや口座残高の正確性を証明しない。

主な履歴件数と純損益は、公式AI 438件・-2,645,924.43円、スズキ124件・+871,630.82円、田中42件・+293,029.85円、guest 3件・+779.78円。ただし古いサーバー実行やテストの履歴が混在する。過去の口座残高・建玉は保存されていなかったため、これらの累計損益から連続運用を復元できない。

監査時の稼働中サーバーでは、guest 3件、田中10件、スズキ6件、公式AI 0件の決済が画面に表示された。田中・スズキの最初の6件ずつは起動時に生成されるデモ履歴で、実際の注文証跡ではない。現在のセッションで確認できた実決済はguest 3件と田中4件だった。

## 実施した作業

1. 稼働中の4口座の現金、建玉、待機指値、自動売買設定をAPIから取り込み、現セッションの決済履歴と合わせて `data/invest_accounts.json` に移行した。
2. 口座状態を定期的に原子的なファイル置換で保存し、起動時に復元するようにした。
3. 個別銘柄ON/OFF、損失停止時の銘柄別決済価格、手動ティックの二重評価、日次損失率の基準額、画面の手数料表示を修正した。デモ取引を履歴に表示し、ランキングにもデモ成績を含む旨を明記した。
4. 日次バッチが別プロセスの一時口座で取引していた処理を止め、常駐APIの取引処理に委譲した。
5. 再起動後に4口座の残高・建玉・件数が復元され、公開URLとローカルAPIがHTTP 200を返すことを確認した。

## 残る制約と次の作業

- 移行元APIは建玉の利確・損切り価格と元の発注者区分を返さなかった。移行済み建玉について、その値は厳密には復元できない。新規建玉では保存される。
- 古いSQLite履歴は現口座の成績に合算していない。過去セッションの残高と建玉が不明なため、合算は誤解を招く。
- 口座ファイルと決済DBは別トランザクションである。今後、単一DBトランザクションと口座別監査台帳へ統合する。
- 田中・スズキのデモ履歴は画面で区別するようにした。実績ランキングから除外するかは仕様を再検討する。
