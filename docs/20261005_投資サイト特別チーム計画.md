# 投資サイト特別チーム計画（2026-10-05）

## 目的

仮想投資サイトの各口座について、誰の操作で何が約定し、残高と成績がどう変わったかを再起動後も再現できる状態にする。公開サイトで他人の口座を操作できる経路を閉じ、デモ・過去検証・現行ペーパートレードを区別する。

## チームと責任

| 担当 | 責任 | 成果物 |
|---|---|---|
| 統合責任者 | 順序、移行、公開前ゲート、横断テスト | 変更計画と検証記録 |
| 口座台帳担当 | 残高、建玉、注文、決済の単一DBトランザクションと復元 | 監査可能な口座台帳 |
| 取引安全担当 | 口座認可、損失停止、指値取消、運用プロセス | 無権限操作・停止回避を防ぐ実装 |
| 成績・UX担当 | デモ分離、ランキング、取引明細、バックテスト表示 | 出自を識別できる成績画面 |
| 独立検証担当 | 再起動、故障注入、二重送信、権限境界、数値再計算 | 受け入れ試験結果 |

## 着手順

### P0: 口座と公開APIの保護

1. 公開APIの変更系操作と個人口座参照に認証・所有者チェックを入れる。`user_id` だけで他人の口座を操作できないことを確認する。
2. 損失判定を指値約定より前に実施する。停止時は待機指値を取消し、同日の再ON・再起動では停止状態を解除できないようにする。
3. 決済、残高、建玉、注文、監査イベントをSQLiteの単一トランザクションへ移す。書込失敗では全変更を戻し、重複要求を一意IDで抑える。

### P1: 成績の信頼性

4. デモ取引を実績集計と順位から分離し、旧DB履歴を別セッション・テストとして隔離する。出所が不明な履歴は推定しない。
5. 取引IDから注文、約定、手数料、為替、純損益、前後残高を追える監査台帳を表示する。
6. 固定値のバックテスト指標を再現可能な結果に置き換える。実行ID、期間、データ版、設定、費用仮定、検証分割を示す。

### P2: 運用安定化

7. 公開サーバー起動時の全 `cloudflared`・ポート8000プロセス強制終了をやめ、このサイトが起動したプロセスだけを管理する。異常時は新規注文を停止し、状態を記録する。
8. 画面・API・ガイドで「現行ペーパートレード」「過去データ検証」「デモ例」を同じ定義で表示する。

## 公開前の完了条件

- 未認証・別口座からの参照、注文、決済、設定変更、リセットが拒否される。
- 停止後に指値が約定せず、当日中の再ONと再起動でも停止が維持される。
- 故障注入・再起動・重複送信後も、残高と建玉が台帳から再計算した値に一致する。
- デモと旧履歴が実績ランキングに混入しない。
- 画面の成績・手数料・取引件数がAPIと台帳に一致する。
- バックテスト指標は同じ入力から再計算できる。未検証値を実績として表示しない。
